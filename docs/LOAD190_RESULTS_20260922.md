# 190-player simultaneous tapping test

## Verdict

Server capacity passed for this run. End-to-end network acceptance is NOT yet
passed: the first tunnel-based join burst timed out, and the remote projection
observer measured a 140 ms P95 update interval (target <=100 ms).
Do not interpret these results as a guarantee for 190 phones at the venue.

## Environment and isolation

- September 22, 2026, Asia/Taipei; report timestamps use UTC.
- Existing DigitalOcean 2 vCPU / 2 GB machine, alongside the production service.
- Isolated app at commit `9537820`, loopback port 3998, transient service
  `luckyhorse-load190`; separate process and in-memory game state.
- This tests the latest local game version, not the still-running production
  version. Production was not restarted, reset, or redeployed.
- 190 Socket.IO clients, five teams of 38, approximately 10 taps/second/client
  during six 8-second tap windows and the 10-second final sprint.
- The successful generator ran ON the VPS via loopback. Its HTTP and tap timings
  exclude mobile/WAN/TLS latency. The generator also consumed VPS resources.
- A Windows Chromium 1920x1080 observer viewed the actual host page through an
  SSH tunnel to Singapore. This is not the public HTTPS path or a real projector.

## Remote rendering and failed attempt

- Completed observer: 2,810 measured racing frames, frame interval P95 18.1 ms;
  99.893% of intervals <=25 ms; 90 distinct sampled character transforms;
  no observed browser window errors. It attached during the match, not before
  the opening countdown. Headless rAF timing is not a physical display/GPU or
  real-phone input-to-paint measurement.
- Remote update interval P95 was **140 ms**, above the 100 ms target. This is
  spacing between received updates, NOT measured one-way latency or tap RTT.
  Network delivery was less regular than local animation. The cause has not
  been conclusively isolated from the SSH tunnel/network path.
- An earlier observer timed out before the match ended because it started
  before the failed join attempt. Its partial data is not a full-match pass.
- Initial Windows-generated burst through a single SSH tunnel connected all
  190 sockets, but only 155 join ACKs and 16 team-selection ACKs arrived before
  the 22.8-second selection deadline. It never tapped or started a game.
  Retained as a failed run, not discarded. The subsequent VPS run cannot prove
  this real-world joining risk is resolved.

`npm test` passed, including 190-player accounting (111,530 checks), realtime
recovery, operation regression, and preflight 13/13. Those checks do not replace
the network or rendering acceptance tests.

## Reproduction and next acceptance

WARNING: the automatic stress tool resets its target before and after running.
Use an isolated instance, NEVER an active wedding game.

```powershell
node scripts/stress-wedding-game.js --url http://127.0.0.1:3998 --clients 190 --tapRate 10 --answerRate 1 --reconnectClients 19 --enforceDuration --report reports/load190-vps.json
```

Run the observer separately with PLAYWRIGHT_MODULE and CHROME_PATH pointing to
installed runtimes; SERVER_URL defaults to the isolated port. REPORT_PREFIX and
OBSERVE_TIMEOUT_MS configure artifact names and the observation deadline.

Before final sign-off, reproduce the 190-client burst and tap workload over an
isolated public HTTPS route without the SSH bottleneck, then rehearse using the
venue network, actual projection computer, and real iPhone/Android devices.
Require <=100 ms P95 projection update intervals, all joins/reconnects, and no
unexplained missing acknowledgements. The current result supports CPU/memory
headroom, but is not an unconditional end-to-end Go.
